# v0.6.0 — 长思考正文分块 + 流式期间改用 contain: layout

这一版解决的是**长思考过程滚动卡顿**，分两条主线：正文落定后按块/按步跳过，正文还在流式增长时只加 containment。

## 一、长思考正文按块跳过（0.5.0）

展开一条很长的思考过程后滚动依然会卡，原因和轨迹页完全不同：整段思考正文是**一个** Markdown 子树，
高度远超视口，所以「按行跳过」永远没有可跳的行——它在视口里，`content-visibility` 就不生效，
每帧都要对整棵子树做一次 style + layout。

把跳过粒度从「行」下沉到「块」：只在思考正文的根上工作，给它高度超过 1.5 屏的直接块子元素
（段落、代码块、列表、表格）逐个打标记。命中根用 `[data-markdown-variant="compact"]`——
DSH 只在思考正文上输出这个属性，普通回答的 Markdown 没有，所以不依赖任何哈希类名。

12 个思考块组 × 42 块、真实类名、headless Edge：

| 指标 | 优化前 | 优化后 |
| --- | --- | --- |
| 每帧脚本+布局中位数 | 3.3 ms | **0.2 ms** |
| 每帧脚本+布局 p95 | 6.3 ms | **0.3 ms** |
| `scrollHeight` | 48512 | 48512（不变） |
| 正文根高度 | 4016 | 4016（不变） |
| sticky 思考头位置 | 41 | 41（不变） |

## 二、PTC 过程按「步」跳过（0.6.0）

PTC 模式下的思考过程不是一个 Markdown 子树，而是一个**过程组**：DSH 把每一轮子调用渲染成组里的
一个 step。0.5.0 的块级跳过在这里粒度不对——真正该跳的盒子是 step，不是 step 里那几十个段落。

0.6.0 因此改成**步级**：先认 `[data-step-process-content][data-chat-flow]`，给它的每个直接子 step
打标记；组外的长思考正文仍按块跳过作为兜底。同时把钉高方式从 `contain-intrinsic-size: auto var(--sb-chunk-h)`
改成直接写字面量 `auto <N>px`——每个被跳过的盒子在每次 style recalc 都要解析一次 `var()`，
实测比字面量慢约 6 倍（18.1 ms vs 2.8 ms）。

40 步 × 70 块：

| 方案 | 中位数 | p95 |
| --- | --- | --- |
| 不优化 | 9.6 ms | 14.6 ms |
| 块级（每步 70 块） | 3.7 ms | 5.8 ms |
| **步级（每步 1 盒）** | **0.2 ms** | **0.5 ms** |

被跳过的**盒子数量**才是成本主因，节点数不是。

## 三、流式期间只加 contain: layout（本次重点）

用户反馈「所有很长的思考过程滚动都卡，尤其是**正在思考中**的时候最卡」。探针逐步定位后得到的结论有些反直觉：

| 每帧 style recalc + layout（单条 3000 块正文，每帧追加 1 个 token） | 中位数 | p95 |
| --- | --- | --- |
| 不加任何东西 | 2.2 ms | 4.8 ms |
| 给每个块打 `content-visibility` | **5.2 ms** | **9.9 ms** |
| **只加 `contain: layout`** | **1.6 ms** | **4.5 ms** |
| 两者都加 | 3.7 ms | 8.1 ms |

正在增长的正文每来一个 token，整条正文都要重排一次。`content-visibility: auto` 在**流式中**
会不断判断「这个块离屏了吗」，这个判断本身就变成每帧的额外开销；而且钉高会随流式不断过期、
不断重写。它只在**内容已经落定、块不再变**的时候才是净收益。

`contain: layout` 不做跳过、不钉高度、不改像素，它只告诉浏览器「这个盒子的布局不会影响外面」，
于是正文内部的重排被限制在这个盒子里，不再扩散到整页。

- 帧级探针（3000 块正文 + 每帧 1 token + 每帧滚动跳变）：旧做法产生 **133 个长帧（29.6%）**，
  新策略 **0 个**；
- 单 token 追加延迟 **2.1 → 1.1 ms**（约 2×）；
- 截图对比 `plain` vs `contain`：**diffpix = 0，bbox = None**——一个像素都没变；
- `scrollHeight` 前后完全一致，行位置无漂移。

现在的分工：

| 状态 | 策略 |
| --- | --- |
| 正文还在流式增长 | 只给正文根加 `contain: layout`，不打跳过标记 |
| 正文已落定 | 走块级 / 步级跳过 |
| 整行已离屏 | 走行级跳过 |

顺带移除了 `topUpStreamingChunks`（流式期间给已钉的块补高），新策略下不再需要，
省掉每帧一次的测量与写样式。

## 四、其它

- 容器/行变更的去抖从 300ms 降到 50ms，切换视图后跟得更快；
- 轨迹表改用静态 CSS 规则（0.4.0 起），JS 属性活不到 DSH 每帧重建 `<tr>` 之后；
- `report()` 新增 `chunks` / `chunkRoots` / `surfaces` 分表面统计，方便判断哪一层生效。

## 兼容性

- **画面不变**：行级 / 块级 / 步级跳过均经截图像素 diff 验证为 0（唯一例外是 B 层
  `will-change: scroll-position` 会把文字从 LCD 子像素抗锯齿切到灰度抗锯齿，这是 0.1.0 起的既有行为，
  更看重逐像素一致可删掉 `applyHints()`）；
- 仅客户端插件，不改 React 组件、不改主题、不卸载任何插件；
- 依赖 DSH 的稳定 `data-*` 属性，认不出来时回退到通用路径，且 `report().surfaces` 能看出认出了什么。

## 安装

```powershell
dsh plugin --profile desktop add "github:TWFU-wcy/dsh-scroll-boost"
```

或从本 Release 下载 `dsh-scroll-boost-0.6.0.tgz`：

```powershell
dsh plugin --profile desktop add ".\dsh-scroll-boost-0.6.0.tgz"
```

装完必须**完全退出并重启 DSH**（不是刷新页面）。之后 Console 执行 `window.__scrollBoost.report()`，
`version` 应为 `0.6.0`。

## 回滚

```js
window.__scrollBoost.disable()   // 立即还原 DOM
```

或装回 `v0.4.1`。
